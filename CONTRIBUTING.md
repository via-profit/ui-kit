## Структура репозитория

Монорепозиторий с двумя пакетами (npm workspaces):

- `packages/ui-kit` — библиотека `@via-profit/ui-kit`, которая публикуется в npm. Документация компонентов лежит в `packages/ui-kit/docs`;
- `packages/ui-kit-website` — сайт документации. Он показывает файлы из `packages/ui-kit/docs` и живые примеры из `src/examples`.

## Разработка

Команды запускаются из корня репозитория:

```bash
npm install        # зависимости обоих пакетов
npm start          # сайт документации в режиме разработки
npm run build      # сборка библиотеки в packages/ui-kit/dist
npm run lint       # линтер обоих пакетов, без исправлений
npm run typecheck  # проверка типов обоих пакетов
npm run i18n       # извлечь и скомпилировать переводы сайта
```

После изменения текстов в примерах сайта запускайте `npm run i18n`, иначе вместо текста на сайте будут идентификаторы сообщений.

В режиме разработки в шапке сайта есть меню стилей: кроме стандартной темы, тестовые темы в стиле Windows 11, macOS и Material Design (`packages/ui-kit-website/src/themes`). Они проверяют, насколько кит поддаётся оформлению через тему, и не входят в пакет. На опубликованном сайте меню скрыто, а выбранный стиль не применяется.

## Проверки

Workflow `.github/workflows/check.yml` запускается на каждый pull request и push в `master`: линтер (`npm run lint`), типы (`npm run typecheck`), сборка пакета, `npm pack --dry-run` и сборка сайта. Сайт собирается из живых примеров, поэтому ломается, если изменился API компонента, а примеры не обновили. Перед push удобно запустить те же команды локально.

Линтер падает только на ошибках, предупреждения его не останавливают.

## Список изменений

Все заметные изменения записываются в `packages/ui-kit/CHANGELOG.md` в раздел «Не выпущено» сразу, вместе с самим изменением. Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/): «Добавлено», «Изменено», «Устарело», «Удалено», «Исправлено».

Изменения, которые требуют правок в коде пользователей, отмечайте в разделе «Изменено» и описывайте, что именно нужно поменять.

## Публикация в npm

Версии следуют [семантическому версионированию](https://semver.org/lang/ru/). Пока мажорная версия равна 0, несовместимые изменения выпускаются как минорная версия (`0.3.0` → `0.4.0`), а исправления — как патч (`0.3.0` → `0.3.1`).

Для публикации нужен доступ к организации `@via-profit` в npm (`npm login`).

1. **Поднимите версию** в `packages/ui-kit/package.json`, например `0.3.0` → `0.4.0`.

2. **Оформите список изменений.** В `packages/ui-kit/CHANGELOG.md` замените заголовок «Не выпущено» на номер версии и дату, а над ним добавьте новый пустой раздел «Не выпущено»:

   ```md
   ## Не выпущено

   ## 0.4.0 — 2026-10-01
   ```

3. **Соберите пакет.** Сборка сначала удаляет `dist`, поэтому файлы удалённых компонентов из прошлых сборок в пакет не попадут:

   ```bash
   npm run build
   ```

   Сборка компилирует TypeScript дважды: в CommonJS (`packages/ui-kit/dist`) и в ES-модули (`packages/ui-kit/dist/esm`). Затем копирует в `dist` файлы `README.md`, `CHANGELOG.md`, `LICENSE` и создаёт `package.json` для публикации: без `scripts` и `devDependencies`, с полями `main`, `module`, `types`, `sideEffects: false` и картой `exports`. Карта перечисляет каждый модуль: сборщики берут ES-модули (`import`), Node и Jest — CommonJS (`require`). Публикуется именно папка `dist`, поэтому компоненты импортируются как `@via-profit/ui-kit/Button`, без `dist` в пути. Пути, которых нет в карте `exports`, импортировать нельзя.

4. **Проверьте содержимое пакета** — список файлов и версию:

   ```bash
   cd packages/ui-kit/dist
   npm pack --dry-run
   ```

5. **Опубликуйте** из папки `dist`:

   ```bash
   npm publish
   cd ../../..
   ```

6. **Зафиксируйте выпуск** коммитом и тегом:

   ```bash
   git add packages/ui-kit/package.json packages/ui-kit/CHANGELOG.md
   git commit -m "chore(release): 0.4.0"
   git tag v0.4.0
   git push && git push --tags
   ```

## Сайт документации

Сайт публикуется в GitHub Pages автоматически: при каждом push в `master` workflow `.github/workflows/deploy-website.yml` собирает его и выкладывает. Запустить публикацию вручную можно на вкладке Actions → «Deploy documentation site» → Run workflow.

Сайт доступен по адресу `https://<владелец>.github.io/<репозиторий>/`, например `https://via-profit.github.io/ui-kit/`.

### Первоначальная настройка

Один раз в настройках репозитория на GitHub: Settings → Pages → Build and deployment → Source — выберите «GitHub Actions». После этого первый push в `master` опубликует сайт.

### Свой домен

1. В Settings → Pages укажите домен в поле Custom domain и настройте DNS по [инструкции GitHub](https://docs.github.com/ru/pages/configuring-a-custom-domain-for-your-github-pages-site).
2. В Settings → Secrets and variables → Actions → Variables добавьте переменную `SITE_BASE_PATH` со значением `/`: сайт будет открываться из корня домена, а не из `/<репозиторий>/`.

### Базовый путь

Сборка сайта читает переменную окружения `SITE_BASE_PATH` — путь, по которому сайт открывается. Без неё сайт собирается для корня (`/`), как при `npm start`. Проверить сборку для GitHub Pages локально:

```bash
SITE_BASE_PATH=/ui-kit/ npm run build:website
```

GitHub Pages не знает о маршрутах сайта и на адрес вроде `/docs/button` отвечает страницей `404.html`. Поэтому workflow кладёт рядом с `index.html` его копию `404.html`: она запускает сайт, и он сам открывает нужную страницу.
